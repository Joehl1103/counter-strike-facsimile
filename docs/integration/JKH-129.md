## Frozen limitations

The captured visual-tool replay is a controlled fixed-step engineering scenario,
not an ordinary full-round or paired CT/T visual acceptance. It may establish
that production-rendered living bots articulate; it cannot establish foot
contact, original Counter-Strike equivalence, or final visual acceptance.

### Runtime oracle correction

The first two candidate captures (`live-skeleton-candidate/` and
`live-skeleton-candidate-2/`) remain retained but are **insufficient**. Their
former metric subtracted each skeleton root from world-space bones, which still
changes when an otherwise frozen skeleton yaws as a whole. Before rerunning, the
oracle was corrected to compare pairwise internal bone distances and to require
the runtime's read-only 5-enemy/4-ally population at both samples. This is a
strictness correction: the old results are not used as candidate acceptance.

### Expanded oracle repair card

Frozen before review-finding repair: 2026-09-16. The independent review found
that caller-supplied server identity, non-failing browser errors, and
name/occurrence subject keys are insufficient acceptance evidence. The expanded
owned paths are `vite.config.ts`, `app/vite-virtual.d.ts`, `app/page.tsx`,
`app/visual-toolkit.ts`, `scripts/verify-live-skeleton-sampling.mjs`,
`scripts/live-skeleton-sampling-contract.mjs`, focused diagnostics tests, and
this report. The production sampling call, M4, simulation behavior, and
performance workload remain unchanged.

The running application must expose a Vite-startup identity derived from its
served `app/page.tsx` bytes and Git revision, with no absolute paths. The
harness must independently compute the expected identity in its own checkout,
compare it to the snapshot, and fail stale or mismatched servers. It must fail
on any page or console error. Each captured bot record must contain stable bot
id, team, alive state, skeleton id, and ordered bone names; the harness must
require identical one-to-one five-enemy/four-ally records at both samples before
using the existing rotation-invariant pairwise-bone metric. A skeleton id must
also belong to exactly one of those bot owners at each sample. Negative controls
cover identity mismatch, browser error, duplicate owner or cross-owner skeleton,
missing/dead ownership, and changed bone sets. The retained `f0605bd` candidate
and diagnostic-control raw reports each already contain nine distinct skeleton
ids at both samples, so this verifier-only strictness amendment needs no new
renderer capture. A separate diagnostic-only control checkout removes only the
live sampling call from this candidate; original JKH-128 remains read-only
historical corroboration. New candidate code/config requires exact source checks
and a quiet-window performance rerun.
