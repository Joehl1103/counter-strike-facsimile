## Scope decision and stop rule

Reuse the existing production clock, input, physics, collision, map, and shared
body-motion modules. A dedicated harness may compose those modules into a stable
route record because the existing isolated measurements do not provide the
issue's same-route proof. Do not substitute direct position teleports for player
physics, relax the 1e-9/1e-12 thresholds, alter scene units, or change the
100 Hz architecture. Repair source only after a failing control demonstrates a
production gap; preserve the baseline trace alongside a repaired candidate.

## Acceptance checklist

- [ ] The seven Dust II routes replay identically at 30/60/144 Hz using one
  recorded timestamped input sequence per route.
- [ ] The composite route record covers the fixed clock, input timeline,
  player physics/collision and rendering interpolation boundary; it is clearly
  labelled as a production-module replay rather than browser FPS evidence.
- [ ] Ramps, steps, ceilings, jump/crouch clearance, falling/landing and
  current weapon movement speeds have focused, meaningful checks.
- [ ] Player and bot ground/support queries agree on the same production world.
- [ ] Any demonstrated defect has a preserved failing control and paired result;
  otherwise no source behavior is changed.

### Unmet fall-damage criterion and minimal next integration

Repository search found no function that derives fall damage from landing speed,
and no health update associated with `movementEvent.landed`. The current shared
page seam at `app/page.tsx` immediately after
`const movementEvent = playerMovement.step(...)` only calls `playLandingCue()`.
The pure `stepCharacterMotion`/`stepPlayerPhysics` path resets vertical velocity
on landing, so the later repair must first preserve an impact-speed value on the
movement event. After a separate numeric approximation/source card freezes a
damage threshold and formula, the smallest integration is:

1. return the pre-reset landing vertical speed through the pure movement event;
2. compute pure fall damage from that event in an owned movement/game-rules
   helper; and
3. at the existing page seam, apply the result through the established player
   health/death handling path exactly once per landing.

`app/page.tsx` is owned by JKH-129 during its graphics capture/review work, so
this branch intentionally makes no page edit. The missing behavior is a
demonstrated baseline gap, not an inference about original CS 1.6 values.
